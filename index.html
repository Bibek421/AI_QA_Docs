From Manual QA to Agentic AI Testing

A practical guide for QA engineers

1. Introduction

AI does not remove the need for QA engineers or manual testing. It changes where human judgment is most valuable and which repetitive activities can be delegated to automation.

Traditional automation follows predefined instructions:

Open the login page → enter credentials → click Login → verify the dashboard.

AI-assisted automation can work from a goal:

Test the login experience for valid, invalid, locked, and unusual user scenarios. Explore the UI, execute appropriate tests, collect evidence, and report important defects.

The strongest QA strategy combines:

  • Human exploratory thinking
  • Deterministic automation for stable, repeatable checks
  • Generative AI for test design, analysis, and content creation
  • AI agents for goal-driven execution and orchestration
  • Human approval for risky or ambiguous decisions

The objective is not “automate everything.” The objective is to achieve fast, trustworthy feedback at an acceptable cost and risk.

2. When manual testing is still necessary

Manual testing is necessary whenever human perception, judgment, investigation, or accountability is more valuable than execution speed.

2.1 Exploratory testing

Use manual testing when the tester must learn the system while testing it. An experienced tester notices unexpected behavior, changes direction, and forms new hypotheses.

Example: While testing an e-commerce checkout, a tester notices that changing the country resets the selected delivery method. This was not in the test case, but it may reveal a state-management defect.

2.2 Usability and user experience

Automation can verify that an element exists, but a person is better at deciding whether a workflow is confusing, frustrating, misleading, or inconsistent.

Example: The “Apply coupon” action technically works, but it is below the fold and gives no visible confirmation. Functional automation may pass; a human may identify a poor experience.

2.3 Visual and emotional judgment

AI visual testing can identify layout differences, but humans should judge brand quality, readability, appropriateness, and emotional effect.

Example: A healthcare error message may be technically correct but unnecessarily frightening to patients.

2.4 New, unstable, or rapidly changing features

Automating an interface before its behavior stabilizes creates high maintenance cost. Early manual exploration helps the team discover expected behavior and select the right future regression checks.

2.5 Complex hardware and physical interaction

Devices, sensors, accessibility equipment, payment terminals, cameras, GPS, poor networks, and environmental conditions often need hands-on testing.

2.6 Accessibility validation

Automated scanners can detect missing labels, contrast issues, and structural violations, but they cannot fully judge whether a keyboard or screen-reader journey is understandable and efficient.

2.7 Security, privacy, ethics, and high-risk decisions

AI and automated tools can find signals, but qualified humans must review high-impact findings and decide whether the risk is acceptable.

2.8 One-time or low-value checks

If a test will run once and is quick to perform, automation may cost more than the value it creates.

A practical decision rule

Situation Recommended approach
Stable, repetitive, high-volume regression Deterministic automation
New or unclear behavior Manual exploratory testing
Many possible inputs with known rules Automation plus generated test data
Usability, accessibility, or emotional quality Human-led, AI-assisted testing
Visual differences across many pages AI visual detection plus human review
Financial, medical, security, or destructive action Automation with mandatory human approval
Unpredictable navigation or frequently changing UI Agentic exploration with strict guardrails

3. How AI can automate manual testing work

AI should be applied to individual QA activities before attempting full autonomy.

3.1 Requirement analysis

An LLM can read a story, acceptance criteria, API specification, design document, and historical defects. It can then identify:

  • Missing or ambiguous requirements
  • Business rules and dependencies
  • Positive, negative, boundary, and abuse scenarios
  • Test-data needs
  • Traceability between requirements and tests

Example input: “A coupon gives 10% off orders above $100 and cannot be combined with another offer.”

AI-generated questions:

  • Is exactly $100 eligible?
  • Is the threshold calculated before or after tax?
  • What happens if the cart drops below the threshold after the coupon is applied?
  • Is the rule the same for every currency?

3.2 Test-case generation

AI can draft tests in natural language, Gherkin, JSON, or framework code. Generated tests must be validated against requirements and business rules.

Scenario: Coupon is rejected when subtotal is below the threshold
  Given a customer has items worth $99.99 in the cart
  When the customer applies the ten-percent coupon
  Then the coupon should not be applied
  And the customer should see the eligibility requirement

3.3 Test-data generation

AI can generate synthetic users, addresses, boundary values, invalid formats, multilingual content, and combinations. Sensitive production data should not be sent to a model without approved controls.

3.4 Converting manual tests into automation

A practical pipeline is:

  1. Read the manual test and associated requirement.
  2. Convert vague steps into explicit actions and assertions.
  3. Discover stable UI or API identifiers.
  4. Select the correct reusable page object, fixture, or API client.
  5. Generate code using the team’s approved templates.
  6. Run the test in an isolated environment.
  7. Repair only safe locator or synchronization problems.
  8. Ask for human review before merging.

AI-generated code should pass the same review, linting, security scanning, and CI rules as human-written code.

3.5 Self-healing locators

When a selector changes, the system can compare attributes, accessible names, DOM relationships, and historical evidence to suggest a replacement.

Bad healing: Silently changing Buy now to a visually similar Cancel order button.

Safe healing: Proposing a candidate, showing the confidence and DOM evidence, rerunning the assertion, and requiring approval when confidence is below a threshold.

3.6 Visual testing

Computer vision can detect clipping, overlap, missing elements, unexpected spacing, broken responsive layouts, and differences from approved baselines. Dynamic areas should be masked, and meaningful differences should be reviewed by a person.

3.7 Failure analysis and defect reporting

AI can group similar failures, inspect screenshots, traces, console logs, network calls, and recent code changes, then draft a defect with:

  • Summary and severity suggestion
  • Reproduction steps
  • Expected and actual behavior
  • Environment and test data
  • Evidence
  • Probable component or owner
  • Confidence and alternative explanations

The model’s diagnosis is a hypothesis, not a proven root cause.

3.8 Risk-based regression selection

AI can connect changed files to services, requirements, tests, ownership, and failure history. It can recommend a smaller test collection while keeping critical paths mandatory.

3.9 We already have Rest Assured, Playwright, Selenium, and Appium. Why do we need AI?

Terminology note: A test suite simply means a group or collection of test cases that are executed together. This guide uses the clearer terms test collection, automated tests, or regression tests instead.

Example: A checkout test collection may contain tests for adding a product to the cart, applying a coupon, completing payment, validating an order, and cancelling an order.

Rest Assured, Playwright, Selenium, and Appium are test execution frameworks. They are very good at performing explicit, repeatable steps and making deterministic assertions. AI is an intelligence layer that can help decide what to test, which tests to run, how to investigate a failure, and how to maintain the tests.

They solve different parts of the quality problem:

Technology Primary job Strongest capability
Rest Assured API automation Reliable HTTP requests and deterministic API assertions
Playwright Modern web automation Fast browser control, auto-waiting, tracing, network control, and multi-browser testing
Selenium Cross-browser web automation Mature ecosystem, broad browser support, and existing enterprise test collections
Appium Mobile automation Native, hybrid, and mobile-web automation across devices
AI layer Reasoning and assistance Test design, semantic analysis, adaptive exploration, failure triage, and maintenance suggestions

The recommended model is:

AI decides or recommends; established frameworks execute; deterministic assertions verify; humans govern.

What existing frameworks already do well

Keep conventional automation for:

  • Stable regression scenarios
  • Exact API, UI, database, and business-rule assertions
  • High-volume parallel execution
  • Performance-sensitive CI feedback
  • Contract and schema validation
  • Compliance checks that require predictable behavior
  • Reproducible tests with clear pass/fail conditions

If a Playwright test reliably validates checkout, replacing it with an LLM-controlled browser would normally make it slower, more expensive, and less predictable.

Problems AI can help solve around the frameworks

Even a mature framework may still have expensive human work before and after execution:

  • Understanding large or changing requirements
  • Discovering missing test scenarios
  • Creating boundary and negative test data
  • Converting approved manual cases into starter automation code
  • Identifying tests affected by a code change
  • Classifying thousands of CI failures
  • Separating product defects from environment and test-script problems
  • Explaining logs, screenshots, videos, and traces
  • Suggesting locator repairs for review
  • Exploring unfamiliar workflows beyond predefined scripts
  • Drafting defects and release-quality summaries

AI targets these bottlenecks; it does not make the execution framework unnecessary.

3.10 Should we switch from our current framework to AI?

Usually, no. Do not rewrite a healthy collection of automated tests merely to call it AI-powered. Preserve the investment in page objects, API clients, fixtures, utilities, device labs, reports, and CI pipelines. Add AI incrementally where it produces measurable value.

Consider switching the underlying framework only for normal engineering reasons—for example, unsupported technology, unacceptable execution time, poor maintainability, missing platform coverage, or an obsolete architecture. “AI is popular” is not a valid migration reason.

Use this decision table:

Current situation Recommended decision
Automated tests are stable, fast, and trusted Keep them; add AI only to selected supporting activities
Automated tests have many flaky failures Fix test design, isolation, waits, data, and environment first; AI may help diagnose patterns
Selenium test collection is valuable but costly to maintain Improve the architecture or migrate selectively based on engineering value; do not assume an AI agent will remove maintenance
Manual regression is large and repetitive Automate stable flows with Playwright, Rest Assured, Selenium, or Appium; use AI to accelerate design and code drafting
Product UI changes frequently Use stable contracts and test IDs first; add reviewed AI locator suggestions or bounded exploration
Team lacks test coverage knowledge Add RAG-based requirement and coverage analysis before autonomous execution
Need unscripted exploration Add a supervised AI exploration agent while keeping deterministic regression
High-risk regulated product Keep traceable deterministic checks and mandatory human approval; use AI as assistance only

3.11 Recommended hybrid architecture with existing frameworks

In this design:

  1. The AI layer reads approved requirements and change information.
  2. It recommends scenarios or selects relevant existing tests.
  3. A policy engine or person approves risky operations.
  4. The existing framework executes the test.
  5. Assertions remain in code whenever the expected result is objective.
  6. AI analyzes evidence and drafts a conclusion.
  7. The final report distinguishes proven facts from AI-generated hypotheses.

3.12 Practical examples for each framework

Rest Assured plus AI

Without AI: A developer writes endpoint tests and manually studies failures.

With AI: The system reads the OpenAPI specification and requirements, proposes missing negative and boundary scenarios, generates a draft Rest Assured test, and summarizes failed request/response evidence. Rest Assured still sends requests and performs assertions.

Example: AI notices that POST /refunds has tests for valid amounts but no test for an amount greater than the captured payment. It proposes the missing case; a QA engineer approves it; Rest Assured executes it on every build.

Playwright plus AI

Without AI: Playwright follows authored browser flows and collects traces.

With AI: AI converts approved scenarios into draft page-object code, recommends impacted tests, interprets traces, and performs a separate supervised exploratory session. Playwright remains the browser execution engine.

Example: When checkout fails, AI correlates the Playwright trace with a 500 payment response and drafts a defect pointing to the payment call instead of simply reporting “button click failed.”

Selenium plus AI

Without AI: A mature Selenium grid runs a large collection of cross-browser regression tests.

With AI: AI groups related failures, detects likely locator changes, and proposes Page Object updates with confidence and evidence. High-confidence suggestions may run in a temporary branch, but they should not silently change the main test collection.

Example: Two hundred tests fail because a shared navigation locator changed. AI identifies the common Page Object, proposes one repair, reruns an affected subset, and requests review.

Appium plus AI

Without AI: Appium performs known interactions on emulators and real devices.

With AI: AI generates device and state combinations, reads screenshots and device logs, identifies likely platform-specific clusters, and guides exploratory flows.

Example: Android tests fail only under a small screen, large font, and dark mode. AI clusters the evidence and identifies a likely layout/accessibility risk; Appium reproduces the exact combination.

3.13 Incremental AI adoption plan for an existing automation team

Stage 1: Measure the current baseline

Record execution time, flakiness, maintenance effort, defect yield, escaped defects, triage time, and automation cost. Without a baseline, the team cannot prove that AI helped.

Stage 2: Introduce low-risk assistance

Start with requirement analysis, test-case suggestions, failure summarization, documentation search, and defect drafting. A human reviews every result.

Stage 3: Connect AI to framework evidence

Provide structured access to Rest Assured request/response data, Playwright traces, Selenium logs, Appium device logs, screenshots, and historical defects. Redact sensitive data and enforce project permissions.

Stage 4: Allow supervised code generation

Generate tests using approved templates, page objects, API clients, naming conventions, and assertion libraries. Run formatting, compilation, linting, security checks, and tests in an isolated branch. Require code review.

Stage 5: Add bounded agent execution

Let an agent execute approved goals only in test environments, with allowlisted tools, limited steps, token and cost budgets, timeouts, and evidence capture.

Stage 6: Expand only after evaluation

Increase autonomy only if evaluation shows accurate tool use, reliable stopping, useful defect discovery, lower maintenance effort, and acceptable cost and safety.

3.14 How to prove whether AI is better

Do not compare tools based on a demo. Run a controlled pilot and measure:

Metric Question to answer
Test-design time Does AI reduce the time from requirement to approved test?
Human acceptance rate How many AI suggestions are accepted with little or no editing?
Defect yield Does the AI-assisted process find meaningful additional defects?
False-positive rate How often does AI create unnecessary investigation?
Flaky-test rate Does the approach improve or damage test reliability?
Mean time to triage Are failures understood faster?
Maintenance effort Are engineers spending fewer hours repairing tests?
Execution time Does AI add unacceptable latency?
Cost per useful result Are model and infrastructure costs justified?
Safety-policy compliance Does the system stay inside permissions and approval rules?

A good pilot compares the normal workflow and AI-assisted workflow on the same representative features. Adopt the AI capability only when it improves a meaningful quality or productivity metric without creating unacceptable reliability, privacy, or security risk.

3.15 Final recommendation for teams with existing automation

Use a hybrid strategy:

  • Keep Rest Assured for API execution and assertions.
  • Prefer Playwright for suitable new web automation while retaining valuable Selenium coverage unless migration has a clear return.
  • Keep Appium for mobile device interaction.
  • Add AI for requirement intelligence, coverage discovery, test drafting, regression selection, exploratory assistance, failure triage, and reporting.
  • Keep deterministic code responsible for objective pass/fail decisions.
  • Require people to approve high-impact changes and ambiguous conclusions.

The best future architecture is not frameworks versus AI. It is frameworks plus AI, connected through controlled tools and evaluated with evidence.

3.16 Complete example using a current automation framework

Assume a team already has:

  • Rest Assured API tests
  • Playwright web tests
  • Appium mobile tests
  • A CI pipeline that runs tests after every deployment
  • PostgreSQL for test results and object storage for screenshots and traces

The new requirement says:

A registered customer can use a 10% coupon when the cart subtotal is at least $100. The coupon cannot be combined with another offer.

Existing approach without AI

  1. A QA engineer reads the story.
  2. The engineer manually identifies scenarios.
  3. They write Rest Assured tests for the coupon API.
  4. They write Playwright tests for web checkout.
  5. They write Appium tests for the mobile checkout.
  6. CI executes the tests and produces reports.
  7. The engineer manually investigates every failure.

This approach is reliable, but requirement analysis, code preparation, test selection, and failure investigation can require significant time.

Improved approach with AI and the same frameworks

Step 1: AI analyzes the requirement

The AI retrieves the coupon requirement, API specification, existing tests, and previous coupon defects. It identifies important questions and cases:

  • Is exactly $100 eligible?
  • Is eligibility based on subtotal before or after tax?
  • What if the cart value falls below $100 after removing an item?
  • What happens when another offer is already active?
  • Does the rule work the same way on web and mobile?

Step 2: A QA engineer approves the scenarios

The engineer removes irrelevant suggestions, answers requirement questions with the product owner, and approves the final test cases.

Step 3: AI drafts framework-specific test code

For Rest Assured, AI drafts an API test such as:

given()
    .contentType("application/json")
    .body(couponRequest("SAVE10", 100.00))
.when()
    .post("/checkout/coupons")
.then()
    .statusCode(200)
    .body("discountPercent", equalTo(10));

For Playwright, AI drafts a test using the team's existing page objects:

test('applies SAVE10 when subtotal is exactly $100', async ({ page }) => {
  const checkout = new CheckoutPage(page);
  await checkout.openCartWithSubtotal(100);
  await checkout.applyCoupon('SAVE10');
  await expect(checkout.discount).toHaveText('$10.00');
  await expect(checkout.total).toHaveText('$90.00');
});

For Appium, AI uses the existing screen objects and proposes the equivalent mobile scenario. The team reviews all generated code before merging it.

Step 4: Existing frameworks execute the tests

Rest Assured validates the API, Playwright validates the browser journey, and Appium validates the mobile journey. Assertions in code—not the AI model—determine whether objective conditions pass or fail.

Step 5: AI assists with failure analysis

Suppose the Playwright test fails because the UI shows $100.00, not $90.00. AI examines the trace and network response:

  • Coupon API response: 200 OK
  • Returned discount: 10
  • Browser console: no error
  • UI total: still $100.00

AI drafts this hypothesis:

The coupon service calculated the discount correctly, but the web UI did not refresh the displayed total after receiving the response.

The report labels this as a hypothesis. The screenshot, trace, response, and deterministic assertion are the actual evidence.

Step 6: Human reviews and publishes the defect

The QA engineer confirms the behavior and publishes the defect. AI saves investigation time, while the current frameworks continue to provide reliable execution and evidence.

Final result

Activity Responsible component
Understand the requirement and suggest scenarios AI assistant
Approve business meaning and risk QA engineer/product owner
Execute API checks Rest Assured
Execute web checks Playwright or Selenium
Execute mobile checks Appium
Determine objective pass/fail Assertions in automation code
Analyze logs, traces, and screenshots AI-assisted triage
Confirm root cause and publish defect QA engineer/developer

This example demonstrates the recommended principle: keep the current automation framework and add AI where reasoning and analysis provide additional value.

4. Essential AI terms for QA engineers

4.1 Generative AI

Generative AI produces new content—text, code, images, audio, or structured data—based on learned patterns.

QA example: Generate boundary tests and Playwright code from acceptance criteria.

Limitation: The output can be fluent but wrong. Always validate it with requirements, executable checks, and human review.

4.2 Tokenization

Tokenization divides text into units called tokens that a model processes. A token may be a word, part of a word, punctuation, or whitespace pattern.

Real-life analogy: Packing a document into small labeled pieces before sending it through a processing line.

Why QA engineers care:

  • Model limits and API cost are measured largely in tokens.
  • Long logs can crowd important requirements out of the context window.
  • Chunking and filtering improve both cost and answer quality.
  • Secrets and personal data remain sensitive even when tokenized.

Example: Instead of sending a 100 MB log, extract the failing time window, correlated request ID, error stack, and surrounding events.

4.3 Embeddings and vector databases

An embedding is a numeric representation of meaning. Similar content tends to have nearby vectors. A vector database stores embeddings and retrieves items by semantic similarity rather than exact keyword match.

Real-life analogy: A librarian who groups books by meaning even when their titles use different words.

QA example: A new failure says “payment authorization timed out.” Vector search may retrieve previous defects about “gateway response delay” even though the words differ.

Common stored items include requirements, test cases, defects, runbooks, code documentation, and failure summaries. Each item should carry metadata such as project, version, service, access level, document source, and timestamp.

4.4 RAG: Retrieval-Augmented Generation

RAG retrieves relevant trusted information and includes it in the prompt before the model produces an answer.

QA example: Before generating tests for refunds, the system retrieves the refund requirement, API schema, existing tests, and related production defects. The model generates tests from this company-specific context instead of relying only on general knowledge.

Good RAG requires quality documents, correct chunking, metadata filters, permission enforcement, reranking, citations, and freshness controls. RAG reduces hallucination; it does not eliminate it.

4.5 MCP: Model Context Protocol

MCP is a standard way for an AI application to discover and use external tools and contextual resources through consistent interfaces.

Real-life analogy: USB provides a standard connection for different devices; MCP provides a common connection pattern for models, tools, and data sources.

QA example: An agent may use MCP-compatible servers to:

  • Read a test case from a test-management tool
  • Control a browser or mobile emulator
  • Query a read-only test database
  • inspect CI results
  • Create a draft defect

MCP is a connection protocol, not the AI model and not the agent itself. Every tool should have explicit permissions, validated inputs, audit logs, timeouts, and safe defaults.

4.6 Temperature

Temperature influences variation in model output. Lower values generally produce more consistent responses; higher values allow more variety.

QA task Typical preference
Generate strict JSON or executable test steps Low temperature
Summarize a failure consistently Low temperature
Brainstorm unusual edge cases Moderate temperature
Explore creative user personas Moderate to higher temperature

Temperature does not measure truth or confidence. A low-temperature answer can still be incorrect. Exact supported ranges and behavior vary by model.

4.7 Prompt engineering

Prompt engineering is the design of instructions, context, constraints, examples, and output formats that guide a model toward a useful result.

A strong QA prompt contains:

  1. Role: “You are a senior payments QA engineer.”
  2. Goal: “Design risk-based checkout tests.”
  3. Context: Requirements, API schema, supported countries, existing coverage.
  4. Constraints: “Do not invent endpoints; mark missing information.”
  5. Output schema: JSON fields or a test-case table.
  6. Quality rules: Include boundaries, negative cases, and requirement references.
  7. Examples: One approved sample when consistency matters.

Weak prompt: “Write tests for checkout.”

Improved prompt: “Using only the attached checkout requirement and OpenAPI schema, generate prioritized API tests. For each test return requirement ID, preconditions, request, expected status, business assertions, risk, and automation suitability. Mark unresolved questions instead of inventing rules.”

Prompt injection is a major testing concern. Retrieved documents and web pages are untrusted data; they must not be allowed to override system policy or tool permissions.

4.8 AI agent

An AI agent is a system that uses a model to interpret a goal, choose actions, call tools, observe results, and continue until it reaches a stopping condition.

Example: “Verify that a new customer can buy an in-stock product.” The agent opens a browser, creates data through an approved API, navigates the product and checkout pages, verifies the order, saves evidence, and reports the outcome.

4.9 Agentic AI

Agentic AI describes systems that demonstrate goal-directed, multi-step behavior with planning, tool use, memory, reflection, and adaptation. An AI agent is a concrete component; agentic AI is the broader behavior or system design.

Real-life analogy: Generative AI is a chef suggesting a recipe. An agent receives the goal “prepare dinner,” checks ingredients, uses kitchen tools, adjusts when an ingredient is missing, and presents the result.

4.10 Deterministic workflow versus agent

Use normal code when the path and rules are known. Use an agent when the route is uncertain and interpretation adds value.

Need Better choice
Run 2,000 known regression tests Deterministic test runner
Explore an unfamiliar UI for risk areas Agent with browser tools
Calculate pass percentage Normal code or SQL
Explain clusters of failures LLM-assisted analysis
Perform a production data deletion Deterministic workflow plus human approval; not an autonomous agent

5. Roadmap: QA engineer to AI testing engineer

Phase 1: Strengthen core QA skills

  • Test design: equivalence partitioning, boundaries, decision tables, state transitions, pairwise testing
  • Exploratory testing and risk analysis
  • API, UI, database, mobile, accessibility, performance, and security fundamentals
  • HTTP, JSON, authentication, logs, networks, and browser developer tools
  • Git and CI/CD basics

Deliverable: A risk-based test strategy for one real product feature.

Phase 2: Learn programming and conventional automation

  • Choose Python or TypeScript
  • Learn functions, classes, asynchronous operations, packages, error handling, and testing
  • UI automation: Playwright, Selenium, or an approved equivalent
  • API automation and contract testing
  • SQL and test-data management
  • Docker and CI execution
  • Page/component objects, fixtures, mocks, and reporting

Deliverable: A maintainable collection of UI and API tests running in CI.

Phase 3: Learn applied AI fundamentals

  • LLMs, tokens, context windows, embeddings, vector search, RAG, temperature
  • Structured outputs and schema validation
  • Prompt design and evaluation
  • Model limitations, hallucination, bias, privacy, security, and cost

Deliverable: A requirement-to-test generator that returns schema-validated test cases with requirement references.

Phase 4: Build AI-assisted QA capabilities

  • Failure summarization and clustering
  • Test-case generation with RAG
  • Synthetic test-data generation
  • Locator suggestions and visual comparison
  • Change-impact and regression selection
  • AI evaluation datasets and quality metrics

Deliverable: A QA assistant grounded in approved project documentation.

Phase 5: Learn agent engineering

  • Tool calling and MCP concepts
  • State machines and workflow orchestration
  • Short-term and long-term memory
  • Planning, retries, timeouts, idempotency, and stopping conditions
  • Human-in-the-loop approvals
  • Observability, security, and cost controls

Deliverable: A supervised test agent that executes a goal in an isolated test environment and produces evidence.

Phase 6: Productionize and govern

  • Multi-tenant access controls
  • Secrets management and audit trails
  • Prompt/model/version tracking
  • Evaluation gates and canary releases
  • Reliability, scalability, disaster recovery, and budget limits
  • OWASP risks for LLM and agent applications

Deliverable: A measurable platform with service-level objectives, security review, and rollback capability.

5–8 Playwright and CI/CD UI regression tests in CI

6. Architecture for an agentic AI automation platform

6.1 Guiding principles

  • Keep deterministic test execution separate from probabilistic reasoning.
  • Treat the LLM as an untrusted decision-support component.
  • Give each tool the minimum necessary permission.
  • Run browser, mobile, and code actions in isolated disposable workers.
  • Require approval for high-risk actions.
  • Store evidence and make every agent action auditable.
  • Measure quality, latency, cost, and safety—not only pass/fail.

6.2 High-level system architecture

6.3 Frontend

Possible technology: React or Next.js with TypeScript.

Core screens:

  • Projects, environments, and access control
  • Requirement and test-case workspace
  • Natural-language goal submission
  • Execution timeline showing planned and completed actions
  • Live browser or device session
  • Evidence viewer for screenshots, video, trace, logs, and network activity
  • Human approval panel
  • Defect review and publishing
  • Analytics for coverage, flakiness, cost, latency, and model quality

Important UX rule: show what the agent intends to do, what it actually did, which evidence supports the conclusion, and what remains uncertain.

6.4 Backend services

A modular monolith is usually the best starting point. Split into services only when scaling, ownership, or security boundaries justify it.

Recommended modules:

  • Identity and access: SSO, RBAC/ABAC, tenant isolation
  • Project service: applications, environments, configurations
  • Knowledge service: ingestion, parsing, chunking, embeddings, retrieval
  • Test management: requirements, cases, test collections, coverage, versions
  • Run service: execution lifecycle, status, cancellation, evidence
  • Agent orchestrator: state machine, planning, tool selection, budgets, stopping rules
  • Model gateway: provider abstraction, prompt templates, model routing, structured outputs, token and cost tracking
  • Tool gateway: approved MCP/tools, input validation, permissions, rate limits
  • Defect integration: draft and publish issues after review
  • Evaluation service: offline datasets and online quality checks
  • Notification service: run completion and approval requests

6.5 Data layer

Storage Purpose
PostgreSQL Users, projects, requirements, tests, runs, defects, approvals, audit metadata
Redis Short-lived agent state, job queues, distributed locks, caching, rate limiting, pub/sub
Vector database Embeddings for requirements, tests, defects, documentation, and failure knowledge
Object storage Screenshots, videos, traces, logs, reports, uploaded documents
Analytics store, optional High-volume run events and historical trend queries

Redis should not be the only durable record of a test run. Persist important state transitions and results in PostgreSQL.

PostgreSQL with a vector extension is often enough for an initial platform. A specialized vector database becomes useful when semantic data volume, filtering, latency, or independent scaling requires it.

6.6 Agent components

  • Planner: converts a goal into bounded tasks.
  • Retriever: obtains relevant requirements, prior tests, and rules.
  • Executor: invokes approved tools.
  • Observer: converts tool results into structured observations.
  • Verifier: checks whether evidence satisfies assertions.
  • Critic: challenges weak conclusions and detects missing evidence.
  • Policy engine: blocks prohibited or high-risk actions.
  • Memory manager: retains run state and approved reusable knowledge.
  • Reporter: produces a traceable result and defect draft.

These are logical roles; they do not require separate LLMs or microservices. Begin with one orchestrated workflow and separate roles only when evaluation shows a benefit.

6.7 Example execution flow

Goal: “Verify that a registered customer can buy an in-stock product using a valid card in staging.”

  1. Authenticate the requester and check permissions.
  2. Retrieve checkout requirements and approved test data rules.
  3. Build a constrained plan and estimate cost/time.
  4. Create isolated test data using an approved API.
  5. Start an isolated Playwright worker.
  6. Navigate the UI using accessible roles and stable identifiers.
  7. Observe UI, network calls, console logs, and backend status.
  8. Assert order confirmation, payment status, and persisted order data.
  9. Save screenshots, traces, tool calls, and assertion evidence.
  10. Clean up test data with an idempotent workflow.
  11. Summarize the result and confidence.
  12. If a failure is found, draft a defect; require review before publishing.

POST   /v1/test-goals
GET    /v1/runs/{runId}
POST   /v1/runs/{runId}/cancel
POST   /v1/runs/{runId}/approvals/{approvalId}
GET    /v1/runs/{runId}/events
GET    /v1/runs/{runId}/evidence
POST   /v1/knowledge/sources
POST   /v1/evaluations

Use server-sent events or WebSockets for live progress. Every mutating request should support authorization, validation, correlation IDs, and—where needed—idempotency keys.

6.9 Security and safety controls

  • Secrets in a secrets manager, never in prompts or source control
  • Separate credentials for each environment and tool
  • Read-only database access by default
  • Domain and endpoint allowlists
  • Sandboxed, disposable workers with time and resource limits
  • Data-loss prevention and personal-data redaction
  • Prompt-injection defenses and separation of instructions from retrieved content
  • Tool schemas with strict validation
  • Approval gates for destructive actions, production access, defect publication, and code merge
  • Complete audit trail of prompts, model/version, retrieved sources, tool inputs, outputs, and decisions
  • Retention and deletion policies for evidence

6.10 Reliability patterns

  • Explicit state machine instead of an uncontrolled reasoning loop
  • Maximum steps, time, tokens, and monetary budget per run
  • Retry only transient failures; use exponential backoff
  • Idempotent test-data setup and cleanup
  • Circuit breakers for unavailable models or tools
  • Dead-letter queue for failed jobs
  • Checkpoints so a run can resume safely
  • Deterministic assertions outside the LLM whenever possible
  • Graceful fallback to a standard test runner or manual review

6.11 Observability and evaluation

Track three groups of metrics:

Test-platform metrics

  • Pass, fail, blocked, and flaky rates
  • Queue time and execution duration
  • Coverage and escaped-defect trends
  • Environment and infrastructure failures

AI quality metrics

  • Test relevance and requirement coverage
  • Unsupported-claim or hallucination rate
  • Retrieval precision/recall
  • Tool-selection and argument accuracy
  • Defect deduplication accuracy
  • Human acceptance/edit rate

Operational metrics

  • Tokens and cost per run
  • Model and tool latency
  • Retry rate
  • Approval frequency
  • Safety-policy violations

Create a versioned evaluation set containing representative requirements, expected tests, known defects, tool tasks, adversarial prompts, and expected safe behavior. Run it whenever prompts, models, tools, retrieval, or policies change.

6.12 Recommended MVP

Do not begin with a fully autonomous multi-agent platform. Build this vertical slice:

  1. Upload or connect approved requirements.
  2. Retrieve relevant context with citations.
  3. Generate structured test scenarios.
  4. Let a human approve selected scenarios.
  5. Execute them through Playwright in an isolated worker.
  6. Collect screenshots, trace, logs, and assertions.
  7. Draft a result and defect for human review.

Suggested starter stack:

  • Frontend: Next.js + TypeScript
  • Backend: FastAPI or NestJS
  • Workflow: explicit state machine; add a durable workflow engine when needed
  • Database: PostgreSQL
  • Cache/queue: Redis
  • Vector search: PostgreSQL vector extension initially
  • Execution: Playwright workers in Docker/Kubernetes
  • Evidence: S3-compatible object storage
  • Observability: OpenTelemetry plus logs, metrics, and traces
  • AI: model gateway with structured outputs, RAG, evaluation, and budget controls

7. Common mistakes to avoid

  • Automating unstable workflows before understanding them
  • Allowing the model to decide pass/fail without deterministic evidence
  • Giving an agent broad production permissions
  • Treating self-healing as permission to hide product changes
  • Storing every interaction as permanent memory
  • Using a vector database without document permissions and metadata filters
  • Sending complete logs when a correlated excerpt is enough
  • Measuring only the number of generated tests instead of defect-detection value
  • Building many agents before a single workflow works reliably
  • Assuming RAG guarantees correctness
  • Letting generated code merge without review and CI checks

8. Interview and training questions with answers

Q1. Will AI replace manual testing?

Answer: No. AI will automate repetitive preparation, execution, and analysis, while humans remain essential for exploration, usability, risk judgment, ethics, and final accountability. The role shifts toward test strategy, evaluation, and supervision of intelligent automation.

Q2. What is the difference between automation and agentic automation?

Answer: Traditional automation follows a predefined path. Agentic automation receives a goal, selects from approved actions, observes results, and adapts within guardrails. Known high-volume checks should remain deterministic; agents are useful when the route requires interpretation.

Q3. What is RAG, and why is it useful in QA?

Answer: RAG retrieves relevant trusted information before generating an answer. In QA it grounds generated tests or failure explanations in current requirements, API specifications, existing coverage, and defect history.

Q4. What is the difference between a vector database and a relational database?

Answer: A relational database is optimized for structured records and exact filtering or joins. A vector database is optimized for semantic similarity. A QA platform normally needs both: PostgreSQL for authoritative test/run records and vector search for meaning-based knowledge retrieval.

Q5. Is MCP the same as an AI agent?

Answer: No. MCP standardizes how an AI application connects to tools and resources. An agent is the decision-making workflow that chooses when and how to use those tools.

Q6. What temperature should test generation use?

Answer: Use a low setting when consistency, structured output, or executable steps matter. Use moderate variation to brainstorm edge cases. Temperature is model-dependent and does not guarantee correctness.

Q7. How do you prevent AI hallucinations in testing?

Answer: Ground outputs with approved sources, require citations, constrain responses with schemas, validate facts and code, use deterministic assertions, run evaluation sets, and require humans to approve high-impact decisions.

Q8. How would you test an AI-generated test case?

Answer: Check requirement traceability, correctness of preconditions and expected results, coverage contribution, duplicate rate, executability, security, determinism, and whether the test detects a seeded defect. Track human acceptance and edits.

Q9. What is self-healing automation, and what is its risk?

Answer: It detects a broken locator or interaction and suggests or applies an alternative. The risk is false healing: the test continues against the wrong element and produces a false pass. Use confidence thresholds, evidence, reruns, and approval rules.

Q10. Why use Redis in an agentic QA platform?

Answer: Redis is useful for job queues, short-lived run state, cache, distributed locks, rate limiting, and real-time events. Durable business records and final results should remain in a persistent database.

Q11. How do you test an AI agent?

Answer: Evaluate task completion, plan quality, tool selection, argument correctness, recovery from failure, stopping behavior, evidence quality, cost, latency, and safety. Include adversarial prompts, unavailable tools, ambiguous goals, and prohibited actions.

Q12. When should a human approval be mandatory?

Answer: Before production access, destructive data changes, external publication, code merge, security-impacting changes, expensive actions, handling sensitive data, or any action with low confidence and high impact.

Q13. Should pass/fail be decided by an LLM?

Answer: Prefer deterministic assertions for status codes, database state, calculations, and UI properties. An LLM may assist with subjective evidence such as message clarity or visual meaning, but its judgment should be bounded, scored, and reviewed when risk is significant.

Q14. How would you reduce the cost of AI testing?

Answer: Use smaller models for simple tasks, filter and summarize context, cache safe results, retrieve only relevant chunks, batch operations, limit agent steps, use deterministic code where possible, and route expensive models only to complex cases.

Q15. What is the best first AI project for a QA team?

Answer: Start with a low-risk assistant such as requirement analysis, test drafting, or failure summarization. Measure accuracy and human time saved. Then add supervised execution after the team has evaluation data and safety controls.

Q16. How do generative AI and agentic AI differ?

Answer: Generative AI creates content from an input. Agentic AI uses generated reasoning within a loop of planning, tool use, observation, and adaptation to achieve a goal.

Q17. What happens if retrieved documents contain malicious instructions?

Answer: Treat retrieved text as untrusted data. Keep system policies separate, restrict tools independently of the prompt, sanitize content, detect injection attempts, and require approval for sensitive actions.

Q18. Why not create multiple agents immediately?

Answer: Multiple agents increase coordination failure, latency, cost, and debugging complexity. Begin with one controlled workflow. Add specialized roles only when evaluation proves that separation improves quality or scalability.

9. Final strategy

The most effective progression is:

  1. Preserve manual testing where judgment and discovery matter.
  2. Automate stable, repetitive checks with conventional frameworks.
  3. Add AI to requirement analysis, test design, data generation, and failure triage.
  4. Ground AI with RAG and company knowledge.
  5. Expose narrowly scoped tools through a secure tool layer such as MCP.
  6. Build a supervised agent around an explicit workflow and isolated test workers.
  7. Evaluate quality and safety continuously before increasing autonomy.

The future-ready QA engineer is not only a test executor. They are a quality strategist who understands product risk, automation, data, AI behavior, system architecture, evaluation, and governance.
